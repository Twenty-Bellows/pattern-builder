# CLAUDE.md

This file provides guidance to Claude Code and other AI coding agents when working with code in this repository.

## Project Overview

**Pattern Builder** is a WordPress plugin developed by [Twenty Bellows](https://twentybellows.com). It allows WordPress users to create, edit, organize, and manage block patterns directly in the admin interface — unifying theme patterns (PHP files) and user-created patterns (`wp_block` posts) in a single, intuitive UI with visual editing, live preview, metadata management, and conversion between the two.

- **Version:** 2.0.0
- **Repository:** https://github.com/twenty-bellows/pattern-builder
- **Issue Tracker:** GitHub Issues — https://github.com/twenty-bellows/pattern-builder/issues
- **Plugin URI:** https://www.twentybellows.com/pattern-builder/
- **License:** GPL-2.0-or-later
- **WordPress Requires:** 6.8+
- **PHP Requires:** 7.4+

## Architecture (Key Design Decisions)

Version 2.0 removed the 1.x DB-mirror + REST-hijacking design entirely. Theme pattern files are the single source of truth; nothing is mirrored into the database and no core REST route is intercepted.

**Theme patterns are file-backed REST entities.** A rowless post type `pb_pattern` (registered like core's `wp_template` — zero DB rows) hangs `Pattern_Builder_REST_Patterns_Controller` off core routing at `/pattern-builder/v1/patterns`. Theme patterns have string IDs (their namespaced name, e.g. `my-theme/hero`), templates-style. Reads come from the pattern files (child + parent theme); writes go back to the files (`Pattern_File_Store`). Because the type is `show_in_rest`, the block editor auto-creates a matching client-side entity from `/wp/v2/types`, which gives theme patterns entity-powered editing (undo, dirty tracking, save flow) for free.

**Editing surfaces — one editor for every pattern.** Both kinds are edited in the post editor: a post editor already on screen swaps either entity into its canvas via `onNavigateToEntityRecord`; everywhere else — the Site Editor included — a pattern opens Appearance → Pattern Builder's edit mode (`&pattern={id}`, plus `&type=user` for a `wp_block`), which boots core's own edit-post editor (`wp.editPost.initializeEditor`) against the entity, with a validated `back` URL whose Back button returns to the originating screen. The Site Editor's canvas is never used, even for user patterns it could host, because theme patterns can never enter it (core hard-codes the entity types its canvas binds and keeps route registration private) and editing both kinds in the same editor is worth more than the nicer canvas for half of them. In that editor a pattern is only its blocks: core's canvas title field is hidden by an editor style (it lives inside the canvas iframe, where page styles never reach) and the document tab's post card by a rule anchored on `.editor-post-card-panel__title` — the pattern's name and description are edited in the Pattern Metadata panel instead. The Appearance page's browse mode is a Site-Editor-style library: a header carrying the Pattern Builder mark and four collection tabs (User / Theme / Uploaded / Community — the last two served by the cloud browser), each with its own search and its own category rail (local pattern categories, or cloud collections); a grid of fixed-size square pattern tiles — the Site Editor's pattern grid: every preview, local or cloud, renders at one design width (1400px) and is scaled into the tile by a constant the stylesheet computes from the two sizes (`src/_pattern-tiles.scss`), so a short pattern is centred and a tall one is cropped at the same point in both grids, with nothing measuring anything in JavaScript. Because that grid renders block previews on a screen that never boots an editor, it has to do two things core's editor screens do for themselves: the page prints the server-registered **block bindings sources** (`Pattern_Builder_Admin`, as `edit-form-blocks.php` does — without those label-bearing stubs core's own `registerBlockBindingsSource()` refuses every source, silently, and a pattern that fills another's slots renders the *other* pattern's placeholder copy), and the browse app registers the read half of `core/pattern-overrides` itself (`src/admin/preview-bindings.js`) since the working half is a private API only an editor boot can reach; the registered patterns reach previews the same way, through `__experimentalBlockPatterns` on the preview provider, or a `wp:pattern` reference renders as "not available". The grid also has an always-present details sidebar whose Save and Edit actions sit at the top above the panels the editor also shows (staged on the entity, persisted by Save; Edit opens the pattern's editor). Creating a pattern starts from a **kind**, listed down the left of one modal under two headings — Design (Design Pattern, Synced Design Pattern) and Starter (Page, Block Starter, Template, Template Part) — in `src/components/patternKinds.js`, which holds the kinds and the request each turns into; `PatternCreatePanel` is the UI. A kind is a starting point, not a stored property: it fixes the metadata its job implies, following the theme handbook's pattern pages, so the modal asks only for what the kind leaves open on top of the name and description every kind takes. A design pattern asks where it is stored (theme file or `wp_block`) and is the only kind that does; the four starter kinds are always theme patterns, because everything that places them is a pattern-file header a `wp_block` has nowhere to put. Each starter kind is one of the handbook's headers: `Block Types: core/post-content` plus `Post Types` (offered when new content is created), a block's own name in `Block Types` (offered when that block is inserted still empty, and from its toolbar), `Template Types` (offered when a template of that type is created — plus `Inserter: no`, since a whole template is noise in the block inserter, as the themes that ship them do), and `Block Types: core/template-part/header|footer` with the matching `Categories`, which is the handbook's own example — those two areas are the only ones WordPress supports, so the field offers exactly two. The last two also take a 1400px `Viewport Width`, the width they are designed against and the width the pattern grid renders at. Blocks are picked with `BlockTypePicker`, core's token field over every registered block: it talks in block *titles* (a title two blocks share carries its name as well) while the file records `core/cover`, and a name typed straight in is kept, since a pattern may name a block this site does not have; post and template types are checkbox grids over fixed vocabularies (`TEMPLATE_TYPES` is core's default template types, shared with the associations panel). Nothing a kind decides is locked in: it all stays editable afterwards in the pattern's own metadata panels. The two panes are two components (`PatternKindList`, `PatternCreateForm`), because the editor sidebar has no room for both at once: there they are two Navigator screens, the kinds list and then the kind's own screen (`/create` and `/create/:kind`), which is what the sidebar's other rows do too.

**Synced patterns via the `core/pattern` content runtime.** Synced theme patterns (`Synced: yes` file header) work exactly like Synced Patterns for Themes 2.0: `core/pattern` gets a `content` attribute + `pattern/overrides` context and a render callback that attaches the pattern's blocks as inner blocks (`Pattern_Block`); `Pattern_Resolver` composes editor-facing content; a synthesized `--synced-instance` companion entry puts a reference in the inserter. Inserted copies are plain `<!-- wp:pattern {"slug":…,"content":{…}} /-->` — no post ID anywhere.

**Companion plugin coexistence.** The runtime classes (`Pattern_Block`, `Pattern_Resolver`, `Block_Markup`, `Inner_HTML_Processor`, `Synced_Patterns`, `Editor_Support`, and the `src/runtime/` JS) are vendored from [`synced-patterns-for-themes`](https://github.com/Twenty-Bellows/synced-patterns-for-themes) and must stay logic-identical to it. Pattern Builder always registers the full stack; when both plugins are installed, the companion sees `PATTERN_BUILDER_VERSION` at `plugins_loaded` and stays entirely unloaded — one check in one place, no coordination anywhere else. Deactivate Pattern Builder and the companion takes over again with identical rendering (both read the same `Synced: yes` header; keeping the vendored runtime in sync at release time is what makes the hand-off invisible). Pattern Builder also clears the companion's transient after file writes so it never wakes to a stale cache.

**Abilities (WordPress core's agent interface).** `Pattern_Builder_Abilities` registers nineteen abilities under `pattern-builder/*` (and `Pattern_Builder_Cloud_Abilities` seven more for the cloud, below) so any agent that can authenticate to the site can drive it — core exposes the registry over REST at `wp-abilities/v1`, and an MCP bridge over that surface gets these for free, which is why there is no bespoke agent API here. Eight reads (`get-authoring-guide` — the pattern-authoring documentation as Markdown, so an agent whose harness has no notion of a "skill" can still be told how to do the job, and the same prose ships as a Claude skill and over the wire; the guides live in `guides/pattern-author/` because `.claude/` does not ship to wp.org, and `.claude/skills/pattern-author` is a symlink to it so there is one copy; the set is filtered before it is served (`pattern_builder_authoring_guides`) so a theme can amend a shipped guide or add its own house rules — which blocks this build settled on, the copy voice — the part general documentation cannot know; the filter deals in text rather than file paths, so a supplied guide needs no filesystem access and no caller can steer a read out of the plugin; `get-design-system` — the whole design system rather than half of it: the merged presets, the **`styles`** a pattern inherits (the root, the elements, the blocks), and the **`blockStyles`** registered here, each marked `portable` — true for one declared in a block's own `block.json`, which ships with WordPress, false for one this site registered, whose definition has to be carried. Presets alone left an agent able to see that a site defines a colour called `ink` and not that the theme paints every heading with it, and the safe move under that blindness is to over-specify: restate the font on each heading, the whole button on each button, none of which then follows the destination; `list-block-types` — what is registered *on this site*, since anything else parses to `core/missing`, and, when it is asked about named blocks, each one's **supports**: the contract deciding which classes its saved markup must carry, which is exactly the half no validator can check because those classes come from filters that only run inside an editor. Supports is about two and a half times the size of everything else in a listing, so naming blocks is what turns it on and a browse stays a catalogue; a name this site does not have comes back under `unknown` rather than as a shorter list; `list-patterns`, `get-pattern`, `render-pattern` — whose answer carries two URLs beside the HTML (`Pattern_Builder_Preview`), because markup shows which classes landed where and nothing about what the CSS then does with them: `standalone` renders the pattern by itself with the site's stylesheets, `page` renders it inside the resolved page template, which is the only way to see whether an `alignfull` band escapes the content width or collapses into it. The page context needs a post to exist, so a stand-in is primed into the object cache for one request and never written; two things make it work and the second is not implied by the first — `core/post-content` checks `$block->context['postId']` and refuses without it, then calls `get_the_content()` with no arguments, which reads the *global* post and the `$pages` globals `setup_postdata()` fills, so the context makes the block agree to render and the globals decide what it renders — plus the two that answer what a pattern can *point* at — `find-media` and `list-fonts`) and nine writes: `create-pattern` and `update-pattern`, which take **finished markup** and persist it, `add-design-tokens`, which is where a pattern's colours, spacing steps and type stack go instead of into its markup — the same `Pattern_Builder_Cloud_Tokens::apply()` a cloud download uses, so the per-type value grammar and the never-overwrite rule are one implementation, with `destination` choosing between the active theme's `theme.json` and Global Styles, `set-global-styles` and `add-block-style-variation`, which are the other two thirds of a design system and are separate abilities for reasons that are not cosmetic — a preset is additive and inert, so a collision is skipped, while there is one `styles.elements.link.color.text` and setting it repaints every page at once, so `set-` replaces where `add-` never does, and folding them together would have meant an ability documented as never overwriting that always does; a variation is a third thing again, a named look applied with a class and scoped to the blocks carrying it, which is what lets it describe a second kind of button (an element style cannot) without fossilising one into the markup (attributes do), and **registration is a file rather than a theme.json key** — `styles.blocks.variations` only *styles* a variation something else registered, since core builds its valid list from the block style registry and `sanitize()` drops a node not in it, so what registers one without PHP is a `styles/{slug}.json` partial carrying a `blockTypes` key. Both refuse raw CSS outright: WordPress does not sanitize a theme.json `css` property, it gates it on `edit_css`, and a string closing its own selector writes rules for the whole document — and what core's schema drops comes back as `skipped` rather than vanishing, since an agent that believes it set a property builds the rest of the design on one that is not there. `set-layout` is the fourth, and the one that is neither a preset nor a style: `settings.layout.contentSize` and `wideSize` are what every constrained band measures its children against, plus `useRootPaddingAwareAlignments`, which decides whether an `alignfull` band escapes the root padding or is inset by it. Settings are not reachable from either of the other writers, and a site left on the wrong measure makes every band restate its own width in markup — the quietest failure in the design system, since nothing errors and the copy merely wraps somewhere else. A width goes through the same value grammar a spacing preset does, because it lands in the same place: core writes it straight into a `max-width` and would quietly substitute `initial` for a value it distrusts, which reads as a layout that did not take. It reports the layout it *wrote* rather than reading it back, because `WP_Theme_JSON_Resolver` keys parsed theme.json files by path and `clean_cached_data()` leaves that cache alone — so within one request the file it has already read is the file it keeps, and a read-back would report the values from before the call. Then the three that put a *file* where a pattern can reach it — `add-asset`, `add-placeholder-image` and `add-font` (below). `add-design-tokens` exists because there was no other way to do it over the wire: `theme.json` is a file with no REST route, and an agent that cannot add a preset inlines the hex instead, which opts the pattern out of the site's palette, its dark mode and every future restyle. Agent input is normalized where a service-built package needed no normalizing — an unknown `type` is *refused* rather than dropped (`missing()` skips a type it does not know, so a silent drop would report writing nothing and the agent would go on to reference a preset that was never created), a slug goes through `sanitize_title()` because core derives the CSS custom property from it, and a missing `name` is filled from the slug because `merge_settings()` writes it unconditionally. **Nothing takes a prompt**: an `execute_callback` that turned a description into a pattern would need a model behind it, which is the inference business this plugin is deliberately out of — the judgement lives in whatever agent is calling, and travels as prose. Validation is likewise absent and cannot be added: `save()` is JavaScript, so the one check most worth offering is the one no server can perform, and the agent must run it before calling `create-pattern` — with `guides/pattern-author/scripts/validate-pattern.mjs`, which loads **the site's own WordPress** (`wp-core.mjs`: the script order comes from core's generated `script-loader-packages.php`, so nothing boots WordPress, and the files go in as real `<script>` elements because these bundles are strict-mode and a strict `eval` keeps its `var` declarations to itself, which loses `ReactJSXRuntime` and every JSX call with it). That means nothing to install but `jsdom`, and — the reason it is worth doing at all — the answer comes from the block library that site actually runs, which is the only version whose opinion counts; bundling the npm packages instead would ship 21MB, because every block's `save()` imports `@wordpress/block-editor` and core keeps each support's `addSaveProps` in the same module as that support's editor UI. `--npm` falls back to `node_modules` where there is no install to find. An agent that only reaches the site over HTTP gets the same check from two more reads: `get-validator` hands over the script itself, and `get-editor-scripts` the site's own script URLs in load order — necessary because WordPress serves those files to anyone but not the graph, core's manifest being a PHP file that a request executes rather than serves, and because the order is not forgiving (the JSX runtime reads `globalThis.React` as it loads, so React arriving late costs every JSX call in the bundles, silently). The scripts are cached by URL, versions included, so an upgrade refetches. The runtime itself is the one thing no server can supply, and Node plus `jsdom` is the stated price of validating at all. The guide index carries a `validate` block naming both abilities and the three writes to run the check before (`create-pattern`, `update-pattern`, `upload-pattern`) — an agent that goes straight to a write reads no guide, so the one step it cannot afford to skip sits where anyone asking what to read sees it first, and a test asserts the abilities it names are registered. Two behaviours of core's are load-bearing: `meta.show_in_rest` must be true or the ability registers but is unreachable over REST, and `meta.annotations` *select the HTTP method* — `readonly` is GET, `destructive` **and** `idempotent` together mean DELETE, everything else POST — so `update-pattern` is deliberately not marked destructive (that word means delete-like here, not "changes data"). Input arrives under an `input` key, not at the top level: `input[key]=value` query args on a GET, `{"input":{…}}` in the body on a POST. Registration is conditional on `function_exists( 'wp_register_ability' )` — the API postdates this plugin's 6.8 floor and no core functionality depends on it, so the REST controller remains the baseline. Agents authenticate with an Application Password, which core only offers over HTTPS or when `WP_ENVIRONMENT_TYPE` is `local` (why `.wp-env.json` sets it).

**Media and fonts an agent can reach (`Pattern_Builder_Assets`, `Pattern_Builder_Fonts`).** A pattern is markup plus the files it points at, and the markup half was the only half an agent could supply — so it invented URLs that 404, pointed at remote placeholder services, or inlined a hex where a font belonged. Four things fix that, and one of them is deliberately **not an ability**: abilities are JSON in and JSON out under an `input` key, so a JPEG would have to be base64 inside that JSON, which means the agent reading the file into its own context and paying for it there. `POST /pattern-builder/v1/assets` takes the bytes as the **request body** with the filename in `Content-Disposition`, exactly as core's `WP_REST_Attachments_Controller::upload_from_data()` does (multipart works too, first file field wins) — so `curl --data-binary @hero.webp` moves a file from disk to the site without it passing through the agent at all. Discovery is the part that had to be designed rather than documented: `find-media` returns the route, its parameters, the limits and a runnable `curl` line in an `upload` key of its own answer, and `add-asset` names it in its description, so an agent looking for an image is told in the same breath how to add one and never has to rediscover it. The other three are ordinary abilities: `add-asset` for the two forms that *do* fit in JSON (SVG markup the agent authored, or a `url` for the site to fetch), `add-placeholder-image`, which draws a plain SVG locally because a pattern pointing at `placehold.co` makes every page view fetch from somebody else's server, and `add-font`. Every answer carries a **`reference`** — the string to put in the markup — because the right string is not guessable: a theme pattern is a PHP file whose assets are composed at render (`<?php echo get_stylesheet_directory_uri() . '/assets/images/hero.webp'; ?>`), and a hard-coded URL breaks the moment the theme moves. Two behaviours are load-bearing and were found by testing rather than by reading: `WP_Image_Editor::get_output_format()` rewrites a filename's extension to match the mime type, so `save()` writes *beside* a `.tmp` file rather than over it and `constrain()` must carry the returned path forward (without which every image over the 2400px cap was stored at full size); and `wp_print_font_faces()` builds its `@font-face` rules from `WP_Font_Face_Resolver::get_fonts_from_theme_json()`, **not** from the font library's posts — so what makes a font render is a `fontFamily` preset carrying `fontFace`, and a font installed without one is a font nothing can use. `add-font` therefore writes the preset in both destinations (through the same `Pattern_Builder_Cloud_Tokens::apply()`, which grew an `extra` key so a preset can carry `fontFace` beside its stack) and additionally creates the `wp_font_family`/`wp_font_face` posts for `user`, so the font is visible and removable where a person would look; the files are self-hosted either way (`assets/fonts` with core's `file:./` placeholder, or `wp-content/uploads/fonts` via `wp_handle_sideload` — a sideload rather than an upload because core skips `is_uploaded_file()` only for that action). **What a family offers has to be askable before it is installed**: `list-fonts` given a `family` describes that one — its weights, its styles, and whether it has a variable face — the same way naming blocks turns on their supports in `list-block-types`, so a browse stays a catalogue. That last flag is the one worth having: the collection serves most families as one fixed file per weight, cut at the family's default optical size, so a design leaning on a variable axis sets wider or narrower than the original with nothing in the markup, the CSS or the computed styles to say why. `add-font`'s answer carries the same `variable` flag for the same reason. The source is core's own registered `google-fonts` collection and nothing else, because every family in it is open-licensed and fetching a font from an arbitrary URL is a licensing decision that is not an agent's to make; `sanitize_value()` already forbids `url(` in a `fontFamily`, so a `src` cannot be smuggled through the token path either. SVG is accepted for the theme and refused for the media library (core does not allow SVG uploads, and enabling it site-wide to satisfy one pattern is a poor trade), scrubbed of scripts, handlers, external references and doctypes on the way in — hygiene rather than a boundary, since `edit_theme_options` already implies running code.

**Migration from 1.x.** `Pattern_Builder_Migration` runs once on upgrade: it rewrites `wp:block` refs pointing at the old `tbell_pattern_block` mirror posts to `wp:pattern` slugs (in post content and theme files), then deletes the mirror posts and the old capabilities.

**Webpack entries:** `PatternBuilder_EditorTools.js` (management: sidebar, panels, save monitor — all block-editor screens), `PatternBuilder_Runtime.js` (the vendored content runtime — enqueued only when this plugin owns it), `PatternBuilder_Admin.js` (the browse grid, plus the edit-mode boot of core's edit-post editor).

**The cloud module (2.1) — patternbuilderwp.com integration.** Users connect their personal [patternbuilderwp.com](https://github.com/Twenty-Bellows/patternbuilderwp.com) account per WP user by signing in (or signing up) **inside wp-admin** — the connect panel posts credentials to this site's proxy, which relays them server-side to the service's `/auth/login` / `/auth/signup` and stores only the returned bearer token (`Pattern_Builder_Cloud`, user meta); the browser never visits the service and credentials are never logged or stored. The service URL is the `pattern_builder_cloud_url` option, overridable by a `PATTERN_BUILDER_CLOUD_URL` wp-config constant — the declarative choice for dev setups like a `.wp-env.json` `config` block, since it survives DB resets — and filterable. The browser never talks to the service: all cloud traffic flows through nonce+capability-gated proxy routes (`/pattern-builder/v1/cloud/*`, `Pattern_Builder_Cloud_Controller`). `Pattern_Builder_Cloud_Porter` converts local patterns ↔ the service's Portable Pattern Package (`pbp/1`): exports bundle local images as `pbp-asset://` placeholders + files — every reference the service checks (`src`, a block attribute's `url`, CSS `url()`), matched by host and path so a query string or an http/https difference doesn't hide one, since anything left pointing at this site is refused there; an image on another host, or one of a type a package can't carry (JPEG/PNG/GIF/WebP only), fails the export with that URL named, while attachment ids and `wp-image-N` classes are dropped on the way out (id 57 names nothing on another site); imports fetch package assets into the media library (a user pattern's blocks are then pointed at the attachments just created; a theme pattern's images move into the theme's own `assets/images` and are referenced from there, so it carries no ids) — always from the configured service origin (asset URLs are re-rooted onto it, never fetched from the host they name, so the service self-identifying by a different URL than the one this site reaches it by just works) — re-sanitize the markup (KSES + scheme checks — never trust the wire), then land as a `wp_block` or flow through `Pattern_File_Store::update_theme_pattern()` for theme destinations. A package says which WordPress it needs (`minWordPress`, which the service derives from the blocks the pattern actually holds), and `version_problem()` refuses an install this site is too old for **before anything is written** — that re-sanitize runs against *this* site's KSES, so an older release does not merely fail to render the unknown markup, it strips it, and the pattern would land looking installed and missing what it was for (MathML is the case that costs content rather than appearance). The browser says so first, from `needsNewerWordPress()` against the `wordPressVersion` the admin page prints; the server is the check that counts. A download that carries design tokens this site lacks shows them first, then writes the missing ones (only those — the server re-checks) into the destination the user already chose for the pattern: theme.json for a theme pattern, Global Styles for a user one. **Block style variations travel the same way** and for the same reason: the markup carries `is-style-{slug}` and the definition lives in the theme it was authored in, so a pattern reaching for one would otherwise arrive with the class intact and nothing styling it. `Block_Style_Variations::carried_by()` gathers what the markup applies — only what *this* site defines, since a variation declared in a block's own `block.json` ships with WordPress and would collide with core's — and `install()` writes the ones the destination lacks, never overwriting, always into the theme (Global Styles has no partials mechanism to register one in, the same reason a dependency always lands as a theme pattern). `collect_tree()` therefore walks one level further down than it used to — markup → `is-style-*` → the definition → the presets *that* references — because a variation's colours are in its definition and none of them appear in the markup. The cloud details card recognizes a pattern already installed locally (link map + a liveness check) and offers *Edit pattern* in place of the download actions. A site option (`pattern_builder_cloud_links`) maps local patterns to cloud IDs so re-uploads offer Update-vs-New. UI lives in `src/cloud/`, mounted behind the browse app's Uploaded and Community tabs (search owned by the browser chrome; the Uploaded rail is the account's collections). **AI generation is not in the plugin.** The service still offers it (`/ai/generations` on patternbuilderwp.com, untouched), but nothing here calls it: the create-pattern modal makes blank patterns only, and there is no `/cloud/generate` proxy. Pulled deliberately, to be reconsidered as a feature later rather than carried half-wired. Connected users also get the **cloud control inside the Pattern Source panel** (`PatternCloudControls`, so it appears in both the browse sidebar and the editor): per-pattern *Upload to the cloud* / *Update pattern on the cloud* / up-to-date, with "changed since upload" tracked by a raw-content hash stored in the cloud-link map at upload time and read back through `/cloud/pattern-state` (link map + hash only — no service round trip). A pattern downloaded from somebody else's is linked but not offered an update: the link map records whose the cloud copy is (`owned` — always true for an upload or a download from the account's own library, otherwise the `mine` the service reported when it listed the pattern), and a refused update marks a link made before that as not ours, so the offer stops coming back. **Uploading is gated on the editor's own block validation** (`src/utils/blockValidity.js`): markup a block type would not have written itself renders correctly but reads as "unexpected or invalid content" the moment any editor opens it — and only a browser can tell, because a block's `save()` is JavaScript and no server can re-run it (`WP_Block_Type` has no `save`; `serialize_block()` replays what it parsed). The panel parses the *saved* markup with `@wordpress/blocks`, disables the button and names the offending blocks; a type this site doesn't have parses to `core/missing` and is left to the service's allowlist. Core answers two questions here and the panel asks both, because `parse()` alone is tolerant: every block keeps its old `save()` implementations (`core/paragraph` has six) and markup matching any of them is accepted and silently migrated. So `parse()` decides what is *invalid* and blocks the upload, while `validateBlock()` — is this what the block writes today? — only warns, since the markup renders and the editor never complains; what it catches is a block-supports class that never made it into the file (`{"backgroundColor":"primary"}` with no `has-primary-background-color` renders with no background at all), and, by comparing the authored attributes against the parsed ones, a setting the migration threw away outright. Two cases are deliberately exempt: an attribute core *relocated* rather than dropped (block library 10.5 moved text alignment into a typography support, so the value lives on under `style.typography.textAlign`), and any block carrying Pattern Overrides bindings, whose content comes from the binding source at render and so cannot be held to a save computed from the file's own attributes. The service approximates the same check in PHP as a backstop (`Pattern_Validator`: attribute JSON that doesn't parse, markup contradicting its attributes). All gating is server-side on the service — the client only mirrors `/me`. The plugin remains fully functional disconnected.

**Names (2.1).** A pattern on the cloud is named `{handle}/{collection}/{pattern}` (the service's D37: the account's handle, the collection's slug, the pattern's slug, each chosen once and permanent), and **that is the name it installs under here**. So a downloaded pattern keeps its cloud name rather than being renamed into this theme's namespace, and `Pattern_File_Store` writes it to `patterns/{handle}/{collection}/{slug}.php` — which is why the theme scan is recursive: core reads `patterns/` to unlimited depth (`WP_Theme::scandir()` with a depth of -1, which never trips the depth guard), so a nested file is a pattern WordPress registers with no help from us, and two accounts' `hero` patterns stop overwriting each other, which is exactly what `get_stylesheet() . '/' . $slug` used to do. The theme's own patterns keep the flat layout every theme uses, because a directory named after the theme, inside the theme, says nothing; `path_for_name()` is the one place that decides. **A bare name is namespaced at the one door every theme-pattern write goes through** (`Pattern_File_Store::update_theme_pattern()`, via `namespaced_name()`), not at each caller: WordPress registers a pattern under whatever its `Slug:` header says, so a bare name used to register something no `core/pattern` reference could reach — and an unresolved reference renders as nothing rather than as an error, so a page assembled from references came out empty with nothing anywhere saying why. A name that already carries a namespace is untouched, which covers both the theme's own and a cloud pattern's permanent three-segment name; the lookup behind `get-pattern` and `update-pattern` answers a bare id with the namespaced pattern for the same reason. Uploading never renames a pattern — `export_local()` sends the last segment of the local name — only the namespace it hangs under changes, and the service refuses the upload outright if that slug is already used in the target collection. The connect panel's signup asks for a handle and both New collection dialogs ask for a slug, each following the name typed above it until it is edited; `handleProblem()` (`CloudBrowser.js`) and `slugProblem()`/`suggestSlug()` (`src/cloud/collections.js`) mirror the service's rules so a form can say no before the round trip, and the service is the check that counts.

**Dependencies and attribution (2.1).** A page pattern is `core/pattern` references to the sections it is built out of, so carrying one means carrying those: the service's collection is a closed world (D38), and this plugin walks the tree at both ends. **Uploading** takes the tree — `Pattern_Builder_Cloud_Porter::local_tree()` walks `core/pattern` slugs through the theme's own files, leaves first (the order the service can accept, since it refuses a pattern naming another until that other is stored — the ordering is the whole transaction, and nothing rolls back because a parent is never stored without its dependencies), and `rewrite_references()` points every reference at `{handle}/{collection}` on the way up, by string substitution rather than a reserialize, which would normalize markup nobody asked to change. Three refusals happen before any request: a reference to a pattern this site does not have, a loop, and a tree that will not fit Personal (`room_for_tree`, since the service refuses one pattern at a time and for a tree that means stopping half way). A pattern that references nothing costs exactly what it always did — no namespace is needed, so no collection is looked up. **Installing** rewrites nothing at all, which is namespacing paying for itself: the reference says `studio-a/heroes/hero`, the file written is `patterns/studio-a/heroes/hero.php` with that `Slug:` header, and it resolves. `install_dependencies()` installs the sections before the page (the package has to be read before its references are known, so the *download* order is root-first and the *write* order is leaves-first), skips any already here under that name — installs are idempotent by name — and always lands dependencies as **theme** patterns even when the page is going to a `wp_block`, because `core/pattern` resolves against the block-pattern registry and a user pattern is not in it. One collection listing answers every reference, since they are all in the same collection. **Attribution** is the `Origin:` file header (post meta for a user pattern), stamped on install in three cases: a package carrying an origin keeps it unchanged, one carrying none from another account gets its cloud name, and one that is the account's own gets nothing — so an origin never names its own account and the Pattern Source panel's line is always somebody else's work. It travels in the file because it has to survive a theme being distributed; the cloud *link* stays in the option map, because that is this site's relationship to a cloud copy rather than part of the pattern. The panel asks `/cloud/pattern-tree` (the same PHP walk) before an upload so it can say "uploads 5 patterns" and run the block-validity gate over every member, and `referencesOf()` from `src/utils/patternTree.js` decides locally whether to ask at all. **There is no move**: `PUT /cloud/library/{id}`, Move to… in both surfaces, the delete-collection move option and the over-policy move line are gone, because a move rewrites the middle segment of a permanent name. **A block style variation is namespaced the same way a reference is**: its slug is a name in a shared namespace exactly as a preset slug is, so two designs both calling something `button-secondary` would collide at any site holding both — and unlike a colour, a wrong variation can restructure the block entirely. `rewrite_variations()` stamps `{handle}-{collection}` onto the slug and onto the `is-style-` class together, by the same string substitution and anchored so `is-style-card` cannot reach into `is-style-card-wide`; the flattening makes the result unparseable back into its parts, which is fine because it is a unique name rather than a path. Stamped once on the way up and never rewritten afterwards, as an origin is — renaming on a re-upload would install a second identical variation beside the first. A pattern authors under the readable local name and the namespace is applied at the boundary, so nothing in the theme has to know about the cloud.

**Collections (2.1).** A collection is the unit of organisation, publishing and installation on the cloud, and Pattern Builder is the only way to get anything out of it (the plan is `docs/collections.md`; the contract is the service repository's `docs/collections.md`, D30–D37). Every uploaded pattern is in exactly one; every account has a locked private **Personal**; a free account's other collections are public from the moment they exist and building one in private is Pro. The proxy (`Pattern_Builder_Cloud_Controller`) relays the service's collection routes — `/cloud/collections` and `/cloud/collections/{owner}/{slug}` for the community, `/cloud/library/collections` with create, update and delete (which takes the collection's patterns with it) for the account's own, a `collection` filter on both listings, `collection` on an upload (`personal` when nothing is asked — the one case the UI asks nothing) and on a download — and relays every refusal as it came, upgrade link included, because the service decides (free: public only; the Personal cap; premium needs Pro) and the plugin only says so. `/cloud/status` carries the service's `entitlements`, the `personal` meter and `overPolicy`; `/cloud/categories` is gone. **Installing** is the porter's: `install_cloud_pattern()` is the one path a download and a whole-collection install share, and `install_collection( $owner, $slug, $destination, $tokens )` walks a collection — skipping what the link map says is already installed from it, carrying on past a failure, collecting per-pattern results — used by the `install-collection` ability, while the browser drives the same steps through `POST /cloud/download` per pattern so it can show "3 of 12". Every pattern installed from a collection carries a **local pattern category named for it**: slug `pbwp-{owner}-{slug}` (a `wp_pattern_category` term for a user pattern, the `Categories:` header for a theme one), with the collection's title remembered in the `pattern_builder_collection_categories` site option and registered on `init`, so the inserter shows the title rather than the slug. The link map (`pattern_builder_cloud_links`) records `collection: { owner, slug, title }` beside the cloud id — what "already installed from this collection" and the tiles' "installed n of m" read. A pattern file's own `Categories:` header travels on `pbp/1` as `inserterCategories`; the old `categories` array is neither sent nor read. In the browser, `CloudBrowser.js` is the shell (connect state, the account bar with Personal's meter, the shared single-pattern download flow as `useDownloadFlow`) and the tabs are their own components: `CommunityTab` (collections first — `CollectionTile` collages of up to four previews rendered exactly as pattern tiles are, a search that shows collections then patterns, `CollectionView` with *Save collection to this site*, and `SaveCollectionFlow`: one destination, one tokens step over the union every pattern needs, sequential downloads with progress, skipped-if-installed, failures listed at the end with the rest installed, the Pro prompt first for a premium collection on a free account) and `UploadedTab` (the rail of the account's collections, Personal first with its meter; a header with rename, describe, visibility as the account may and delete-with-its-patterns; New collection, which tells a free account the collection will be public and why; the over-policy banner for a lapsed Pro). `CollectionPicker` is the upload's picker with *New collection…* inline, in `PatternCloudPanel` (default: the collection used last, kept in `localStorage`; nothing is asked with only Personal; a public target says so). The arithmetic — the token union, what to skip, what results add up to, the default collection — is `src/cloud/collections.js`, tested on its own. **Seven cloud abilities** (`Pattern_Builder_Cloud_Abilities`, D33): `list-collections`, `get-collection`, `search-cloud-patterns` (GET) and `install-collection`, `install-cloud-pattern`, `upload-pattern`, `create-collection` (POST). All run as the WordPress user the application password names and use that user's connection — two people have vouched, and the agent never holds a cloud credential — and without one refuse with `pattern_builder_not_connected`. `create-collection` is always private, so on a free account the service refuses it with the upgrade message (an agent never publishes); no ability changes a visibility or deletes a collection. Tests mock the service with `pre_http_request`, as every cloud test does; `tests/e2e/cloud-roundtrip.php` uploads into a collection and, run on a second site with `install {owner}/{slug}`, installs it.

**Accounts, checkout and telemetry (2.1).** Three things the connect panel and the cloud tabs do that the service decides and the plugin only relays. *The Community tab is browsed as an account*: the service lists its directory to anyone, but here both cloud tabs show the connect panel until a token exists and the proxy enforces the same rule (`/cloud/directory`, `/cloud/collections` and a directory `/cloud/download` answer 401 disconnected) — so what a site downloads is downloaded by somebody, which is the funnel; the website's directory stays public. *Creating an account* applies the service's password rule (eight characters with an upper-case letter, a digit and a symbol — `passwordProblem()` in `CloudBrowser.js` mirrors it so the form says what is missing before the round trip, and the service's `Password_Policy` is the check that counts), asks the marketing question as two buttons with neither preselected (a pre-checked box is not consent under GDPR and reads as opt-out to the wp.org review team; no answer relays as `no`), and leaves the account unverified until the emailed link is opened — `/me` reports `account.verified`, the cloud bar shows a resend nag, and the service refuses uploads, community downloads and upgrades until then. *Forgot your password?* posts the address to `/cloud/password/forgot`, an unauthenticated relay to the service's `/auth/password/forgot`; the emailed link finishes the reset on patternbuilderwp.com, never here. *Go Pro* opens Freemius's overlay checkout on the Pattern Builder screen (`src/cloud/checkout.js`): the service's `/me` carries a `checkout` configuration (product, plan, public key, the account's email as `readonly_user`, sandbox parameters only where the service host allows them), Freemius's script loads on the first click and never before — it is the one third-party script this plugin loads, permitted by wp.org guideline 8 as a documented service on its own domain, and the readme's External services section says so — and `purchaseCompleted` posts the licence id to `/cloud/billing/sync`, which relays to the service's `/billing/sync` so Pro is on before the overlay closes; the hosted checkout URL stays as the fallback and the status poll as the safety net. *Usage telemetry* (`Pattern_Builder_Telemetry`, `src/utils/telemetry.js`, `TelemetryPrompt`) is opt-in because wp.org guideline 7 requires explicit consent: the browse app asks once per site with Allow and No thanks (`TelemetryPrompt`, a site option recording who decided and when), a site that declined is offered it once more as a one-line Allow on the connect panel, and `track()` is a no-op until the answer is yes. When allowed, named events (`browser_opened`, `pattern_created` with its kind, `community_browsed`, `cloud_browsed`, `pattern_uploaded`, `pattern_downloaded`, `account_connected`, `upgrade_opened`, and the activation/deactivation of an already-consenting site) carry the environment — plugin, WordPress and PHP versions, locale, theme slug, multisite, environment type, plus the connected account id — under a random install id minted at opt-in; never the site's URL or name, never content. They are buffered per request and posted once on `shutdown` to the service's public `/telemetry` relay (non-blocking; a lost batch is lost), which keeps a fixed allowlist of names and property keys and forwards to PostHog — so the plugin names one service and loads no analytics script. The connect panel keeps working disconnected; the community does not.

## Architecture Overview

### Plugin Structure
The plugin follows a component-based OOP architecture with clear separation of concerns:

1. **Main Entry Point**: `pattern-builder.php` initializes the plugin
2. **Core Class**: `Pattern_Builder` (singleton in `includes/class-pattern-builder.php`) bootstraps all plugin components
3. **Component Classes** (`includes/`):
   - `Pattern_Builder_Entity` - Rowless `pb_pattern` post type registration
   - `Pattern_Builder_REST_Patterns_Controller` - String-ID REST controller for theme patterns
   - `Pattern_File_Store` - Reads/writes pattern files; image import/export; conversions
   - `Pattern_Builder_API` - The `/pattern-builder/v1/process-theme` endpoint
   - `Pattern_Builder_Admin` - Appearance → Pattern Builder: browse grid + core-editor boot
   - `Pattern_Builder_Editor` - Block editor asset integration
   - `Pattern_Builder_Migration` - One-time 1.x → 2.0 upgrade
   - `Pattern_Builder_Security` - File-path validation and safe filesystem helpers
   - `Pattern_Builder_Abilities` - WordPress Abilities API registrations (conditional)
   - `Pattern_Builder_Cloud_Abilities` - The seven cloud abilities, through the WordPress user's own connection (conditional)
   - `Pattern_Builder_Cloud`, `Pattern_Builder_Cloud_Controller`, `Pattern_Builder_Cloud_Porter`, `Pattern_Builder_Cloud_Tokens` - The patternbuilderwp.com client: token store, proxy routes, package conversion, design tokens
   - `Pattern_Builder_Theme_Json` - The two places a theme.json-shaped config lives (the active theme's file, the site's Global Styles) behind one load/save/edit door, so the token writer and the style writer share the four ways loading can fail rather than each knowing that one destination is a file and the other a post
   - `Pattern_Builder_Theme_Styles` - The `styles` half: a deep merge that replaces at each property it names, the `css` refusal both writers share, and the report of what core's schema dropped
   - `Pattern_Builder_Block_Style_Variations` - The theme's `styles/*.json` partials: writing one, reading a definition back by slug, the slugs a pattern's markup applies, what an upload has to carry, and the never-overwrite install
   - `Pattern_Builder_Assets` - Finding, receiving and storing the images a pattern references, plus the one route that takes binary
   - `Pattern_Builder_Preview` - The route that renders a pattern as a whole page with the site's styles, standalone or inside the page template

**Themes for pattern development (`themes/`).** Two block themes that ship with the plugin and that nothing registers or activates: `blank-theme`, which has no presets, no styles and templates that constrain nothing, so a pattern rendered against it shows what the pattern itself does; and `opinionated-theme`, which is the worked example of `references/design-system.md` — the slugs that guide says are safe (`base`/`contrast` and `accent-1..3`, the `small`…`xx-large` ladder, the numeric spacing scale) at values that are nobody's defaults, so a pattern referencing them correctly looks *different but right* and one hard-coding a hex looks wrong. Opinionated and deliberately *not* broken, since `alignfull` still escapes and a template that capped every band would teach the wrong lesson. A pattern travelling through the cloud carries its tokens with it — an upload looks every referenced preset up in the *authoring* site and ships its value, a download installs the ones the destination lacks and leaves the rest — so the discipline is that every preset a pattern references exists where it is written, and `render-pattern` reports the ones that do not under `tokens.undefined` (a slug `Cloud_Tokens::collect()` cannot find is skipped silently, so the pattern arrives referencing nothing). The preview renders against either theme without activating it (`theme=` on `/preview`, relayed by `render-pattern`'s answer), carrying the pattern's own presets in by the same never-overwrite rule a download follows — which is what makes the blank render mean something: the pattern's own values with nothing on top is its intent, rather than every reference resolving to nothing. the swap filters `stylesheet`/`template` and their directories for one request and **registers the plugin's themes directory as a theme root**, without which `WP_Theme_JSON_Resolver` goes through `wp_get_theme()`, fails to construct the theme, and returns its settings emptied of every preset, its layout and appearanceTools — which reads as a theme that declared nothing rather than one that could not be found. A bundled theme exposes `{slug}_boot()`/`_unboot()` because `require_once` runs a file once per process, so filters attached in the file body would attach for the first preview and no other. It also ships one block style variation of its own (`styles/inset-panel.json`), because the guide now covers three layers rather than one. A pattern that renders correctly in both travels. They live in the plugin rather than `dev-assets/` so they are present wherever it is, including on a site an agent only reaches over HTTP; `blank-theme` needs a `functions.php` because `theme.json` cannot make a theme blank on its own — `settings.color.defaultPalette: false` hides core's colours from the editor's picker and governs whether a theme may reuse their slugs, and does *not* stop `--wp--preset--color--vivid-red` being emitted, so core's presets are emptied through `wp_theme_json_data_default` instead, and the test asserts that against the generated custom properties rather than the JSON.
   - `Pattern_Builder_Fonts` - Installing a self-hosted typeface from core's Google Fonts collection, and the preset that makes it render
   - `Pattern_Builder_Telemetry` - Opt-in usage reporting: the site's answer, the install id, the shutdown batch to the service's relay
   - `Pattern_Builder_Localization` - i18n support
   - Vendored runtime (kept identical to synced-patterns-for-themes): `Pattern_Block`, `Pattern_Resolver`, `Block_Markup`, `Inner_HTML_Processor`, `Synced_Patterns`, `Editor_Support`

### Frontend Architecture
- **Build System**: Webpack via `@wordpress/scripts` with three entry points:
  - `src/PatternBuilder_EditorTools.js` - Editor tools (sidebar, document panels, save monitor)
  - `src/PatternBuilder_Runtime.js` - The vendored core/pattern content runtime
  - `src/PatternBuilder_Admin.js` - The Appearance → Pattern Builder page (browse grid + edit-post boot)
- **React Components** in `src/components/`:
  - `PatternBrowserPanel` - Main pattern browsing interface
  - `PatternCreatePanel` - Pattern creation flow: kinds of pattern on the left, the chosen kind's description and its remaining fields on the right (kinds defined in `src/components/patternKinds.js`)
  - `BlockTypePicker` - Picks block types by title from everything registered on this site (the `Block Types` header)
  - `PatternPreview` - Pattern preview rendering
  - `BlockBindingsPanel` - Block bindings configuration panel
  - `PatternAssociationsPanel`, `PatternSyncedStatusPanel`, `PatternMetadataPanel`, `PatternPanelAdditions`, `PatternSourcePanel` - Editor sidebar panels (also reused by the browse page's details sidebar)
  - `PatternCloudPanel` - The per-pattern cloud upload/update control, rendered inside `PatternSourcePanel` (connected users only), with the collection picker and the tree summary an upload would carry
  - `TelemetryPrompt` - The once-per-site Allow / No thanks question, and the one-line second offer the connect panel shows a site that declined
  - `PatternCard`, `PatternDetailsPanel` - The browse grid's square cards and details sidebar
  - `EditPatternToolbarButton` - "Edit Pattern" in the toolbar of synced theme pattern instances
  - `EditorSidePanel` - Editor sidebar container
  - `PatternList` - Pattern list/grid view
  - `PatternBuilderConfiguration` - Plugin settings UI
- **Admin app** in `src/admin/`: `App`, `PatternBrowser`, `editor-boot`
- **Cloud** in `src/cloud/`: `CloudBrowser` (the shell: connect panel, account bar, the shared download flow), `CommunityTab`, `UploadedTab`, `CollectionTile`, `CollectionView`, `SaveCollectionFlow`, `CollectionPicker`, `collections` (the pure helpers), `checkout` (the Freemius overlay)
- **Telemetry** in `src/utils/telemetry.js`: `track()` and the consent state the PHP side printed
- **The dependency walk** in `src/utils/patternTree.js`: `referencesOf()`, `treeOf()` leaves-first with cycle detection, and `rewriteReferences()` — the browser's copy of what `Pattern_Builder_Cloud_Porter` does server-side, so the panel can say what an upload will carry without a round trip
- **Vendored runtime** in `src/runtime/` (keep identical to synced-patterns-for-themes `src/`)
- **State Management**: core data stores (`core`, `core/editor`, `core/block-editor`) — no custom store

### Pattern Handling
- Supports both **theme patterns** (PHP files in `patterns/`, child and parent theme) and **user patterns** (core `wp_block` posts)
- Abstract pattern class (`src/objects/AbstractPattern.js`) provides unified interface
- Pattern syncing capabilities between theme files and database

### REST API
Endpoints registered under `/wp-json/pattern-builder/v1/`. Authentication via WordPress nonce system.

### Key Development Patterns
- PHP classes follow WordPress coding standards with proper namespace (`TwentyBellows\PatternBuilder`)
- JavaScript follows WordPress/Gutenberg patterns using `@wordpress` packages
- Assets enqueued with proper dependency management using `.asset.php` files generated by Webpack
- Security: nonce verification on all state-changing operations, capability checks, data sanitization

## Coding Standards

- **`docs/` is living.** Every document there describes how the system works **now**, and a change that makes one wrong is not finished until that document is right — corrected in place, not annotated. The service repository's `docs/decisions.md` is the single exception: it is a log, so entries stay as written and a later one supersedes an earlier. A dated "approved design" or "the plan" heading records when something was agreed; it does not mean the page has stopped being true, and it is not a reason to leave it stale.
- **PHP**: WordPress Coding Standards (WPCS 3.x) via PHPCS. Config: `phpcs.xml.dist`
- **JavaScript**: ESLint via `@wordpress/scripts` defaults, extended by `eslint.config.cjs` (flat config, as ESLint 9 requires) for one thing only: `src/runtime/` is vendored and must stay logic-identical to synced-patterns-for-themes, so two rules that disagree with how that upstream is written are turned off *there* and nowhere else
- **Jest**: `jest-unit.config.js` extends the `@wordpress/scripts` config to compile `node_modules` and `.mjs`. Much of the WordPress dependency tree now ships ESM only, and Jest cannot `require()` an ES module before Node 24.9 — without this the suite fails to *load* rather than failing a test
- **CSS/SCSS**: Stylelint via `@wordpress/scripts` defaults
- **Formatting**: Prettier (wp-prettier) for JS/CSS
